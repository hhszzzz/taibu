# 太卜工程与设计规范

本目录是太卜研发规范的统一入口。它约束新代码、重构和评审，也解释为什么项目采用当前的模块边界与验证方式。

> 本文描述规范本身；运行架构见 [项目架构](../manual/Architecture.md)，Agent 专项契约见 [Agent 手册](../manual/Agent.md)，算法口径见 `packages/core/ALGORITHM_RULES.md`。

## 1. 规范用语与效力

- **必须 / 禁止（MUST / MUST NOT）**：涉及正确性、安全、数据归属、公共契约或一致性的硬性要求。违反时不能合入。
- **应该 / 不应该（SHOULD / SHOULD NOT）**：默认做法。确有更优方案时可以偏离，但需在变更说明中交代理由和验证方式。
- **可以（MAY）**：可选项，不代表推荐所有场景都采用。

规范不是“新代码才尽量遵守”的建议。触碰旧代码时，应让修改区域达到规范；发现影响权限、数据或公共行为的例外，先处理再扩展功能。纯文案或极小修复不强制扩大重构范围。

## 2. 事实来源与冲突处理

按以下顺序判断，不用外部博客或历史印象覆盖当前事实：

1. **可执行契约**：当前数据库 SQL、公开 API/Core 类型、架构守卫、通过验证的测试。
2. **项目专项规范**：本目录、Agent 手册、算法规则、自托管手册及已确认的设计规格。
3. **框架与标准的一手文档**：Next.js、React、PostgreSQL、W3C、OWASP 等当前版本文档。
4. **其他项目实践与社区建议**：只能作为设计输入，必须结合本项目验证后采用。

代码与文档冲突时，不默认代码一定正确：先判断是实现漂移还是文档过期，再同步修正二者。任何新实测、新裁决或新公共契约都应更新对应规范，不能只留在对话里。

## 4. 当前约束与目标规范必须区分

文档中的“当前实现”是仓库已存在的事实；“目标规范”是后续实施时应达到的状态。目标组件、依赖、命令或自动检查在真正落地前，不得写成已可用，也不得在业务代码中提前引用。

目前仓库已有：

- Tailwind v4、语义令牌、明暗主题、字体档位与减少动画支持；
- `Modal`、`Dialog`、`Toast`、`Tooltip`、`Select`、`Menu`、`Popover`、`StatePanel` 等共享实现；
- TypeScript strict、ESLint、架构守卫和分层测试；
- Better Auth、ScopedDb、PostgreSQL RLS、Redis/BullMQ 与 Worker 边界。

shadcn registry + Base UI 已用于基础组件建设：设置中心、后台管理、通用业务页、聊天菜单/浮层与表单控件已迁移；`src/components/ui` 之外不再有原生按钮、文本输入或 textarea。聊天 composer 与 Agent 工作区的实测几何、盘面与占术专用控件保留领域样式，但交互统一走共享组件。可用组件、覆盖范围与例外以 `components.md` 与 `src/components/ui` 当前源码为准；必须保留太卜视觉令牌，不能导入 shadcn 默认主题把全站换成另一套皮肤。

## 5. 变更的基本工作流

### 5.1 动手前

1. 明确用户行为、公共契约和验收标准，先检索现有组件、流程、接口与测试。
2. 阅读将修改区域的规范；涉及 Next.js、第三方库或数据库时核对其当前一手文档。
3. 判断变更属于文案/样式、组件交互、业务逻辑、API、数据权限还是基础设施。
4. 对高风险重构先补现有行为回归，再改实现；不得边重写边悄悄改变业务语义。

### 5.2 实施中

- 单一变更组解决一类问题；重构与无关功能分开，保持差异可审查。
- 复用公共边界，不在页面、路由或 Worker 中复制另一套实现。
- 新规则应尽量能由类型、测试、lint 或架构守卫执行；不能自动化的进入评审清单。
- 同步更新调用方、测试与文档。旧实现完全替代后删除，不保留长期平行入口。

### 5.3 完成前

按 [测试与验收](testing.md) 选择验证层级，并在变更说明中回答：

- **改了什么**：用户或调用方可感知的变化。
- **为什么改**：问题、目标或规范依据。
- **如何验证**：实际执行的命令、路径、视口/主题和结果。
- **风险与回滚**：公共契约、数据、兼容和部署风险；没有则明确写“无”。

不能只写“已测试”“应该没问题”。未执行的检查要说明原因，失败项必须如实保留在交付说明中。

## 6. 最低验证矩阵

| 变更类型 | 最低要求 |
| --- | --- |
| 文档 | 检查链接、事实与当前代码一致；目标方案明确标注 |
| 纯文案/局部样式 | 相关页面手动验证，覆盖明暗主题与受影响视口 |
| 共享 UI/交互 | 浏览器行为回归 + 真实页面键盘/响应式/视觉走查 |
| `src/lib/*` 业务逻辑 | 新增或更新单元/契约测试 |
| `src/app/api/*` | 路由测试，成功、失败、权限边界至少覆盖两类；鉴权/积分/会员/限流需专项回归 |
| 数据库/RLS | 隔离 PostgreSQL 契约、备份/升级验证、当前 SQL 与生成类型同步 |
| 跨层或发布前变更 | 完整 `pnpm verify`，需要时补真实栈验收 |

## 7. 例外与规则演进

例外必须满足三点：**范围窄、理由具体、有失效条件**。禁止“历史原因”“特殊处理”这类永久笼统豁免。

需要偏离公共规范时，在变更说明中记录：

- 受影响的文件、组件或路由；
- 为什么现有公共方案不适用；
- 安全、可访问性与回归验证；
- 何时可以收敛回公共方案，或由谁负责把例外提升为新规范。

规范变更与代码变更保持同一事实来源。只改文档而不改实现时，应明确这是目标约定；只改实现而不改文档时，不能声称规范已经升级。

## 8. 外部参考的使用原则

本项目参考 Supabase 的共享 UI 与模块化规则、Cal.com 的严格类型和可审查变更实践，并采用 W3C、OWASP、Conventional Commits 等公开标准。参考不等于复制：其他项目的数据库、部署、翻译、PR 大小或许可流程不自动成为太卜规则。

关键外部依据链接在各专项文档末尾给出。经验性建议若没有项目内验证，不应包装成绝对结论。
