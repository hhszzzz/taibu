# 代码风格、依赖与变更规范

本文解决跨前后端的一致性：类型、命名、模块、注释、依赖、重构、提交和评审。目标是让代码表达意图和边界，而不是追求表面统一或抽象数量。

## 1. 总原则

- **清晰优于技巧**：优先直白控制流和明确数据形状，不用隐晦推断、长链式表达式或过度泛化展示能力。
- **复用优于重复**：先找现有实现；复制公共逻辑会造成权限、算法和交互契约漂移。
- **类型表达约束**：让非法状态尽量无法表示，而不是运行后靠注释提醒。
- **局部性优于过度抽象**：只有真实复用或明确边界才抽模块，不把每三行代码都提成 util。
- **变更可解释**：重构、功能和格式调整尽量分开，评审者能判断每项修改与目标的关系。

## 2. TypeScript

### 2.1 类型纪律

- 保持 `strict`、`noUnusedLocals`、`noUnusedParameters` 通过，不新增无必要 `any`、`@ts-ignore`、`@ts-expect-error` 或非空断言。
- 外部输入使用 `unknown` 起步，经运行时校验/解析后得到准确类型；不能把 fetch JSON、模型输出、队列 payload 直接断言成业务接口。
- 类型断言只在编译器无法得知但代码已建立不变量时使用，并尽量靠近校验；连续 `as Foo` 不能替代解析。
- 可空、可选和默认值语义不同：缺少字段、字段为 null、空字符串和 0 不得混为一谈。
- 跨模块公共契约使用显式类型，内部简单推导可保留；避免深层类型体操掩盖业务形状。
- `import type` 用于纯类型导入，减少运行时副作用与循环依赖。

### 2.2 建模方式

- 状态有互斥关系时使用判别联合，例如 idle/loading/success/error，不用多个可随意组合的布尔值。
- 字符串枚举使用联合或现有领域类型，不让任意字符串进入 action、来源、角色和状态。
- 泛型保留真实类型关系；如果泛型只是把 `any` 传到另一层，应重新设计。
- 不在宽泛 catch 中丢失错误身份；需要分类时使用项目错误类型或安全归一化边界。
- 不在业务对象中混入 transport、数据库和 UI 字段；跨层需要时定义明确映射。

## 3. 命名

- 名称描述领域事实：`requireAdminContext` 比 `checkUser` 更准确，`createAIAnalysisConversation` 比 `saveData` 更明确。
- 布尔值使用 `is/has/can/should` 或状态含义；事件回调使用 `onXxx`，实际处理函数使用 `handleXxx` 或领域动作。
- 服务端文件使用 `.server.ts` 表明边界；hooks 使用 `useXxx`；组件与主要文件同名。
- 测试文件描述被测对象，测试名描述条件与结果，不写 `test 1`、`works`、`fix bug`。
- 避免 `data`、`info`、`item`、`temp`、`helper`、`common` 作为长期公共模块的唯一语义。
- 不在日常命名中携带供应商、参考站或一次性迁移来历；名称应说明当前职责。

## 4. 模块、导入与导出

- 优先直接导入具体模块，避免无约束 barrel 重新导出整个领域、引入循环或扩大客户端包。
- 命名导出为默认；框架要求的 page/layout/config 等保留默认导出。
- 导入顺序保持文件现有一致风格：框架/外部依赖、项目公共层、同领域相对模块、类型与样式。
- 不跨层 import：UI 不读 DB，Core 不读 Web，Route 不读页面组件，浏览器不读 `.server.ts`。
- 新文件先确定唯一事实来源，禁止通过 re-export 永久维持多个“看起来都可用”的入口。
- 生成文件只由对应生成命令修改；生成器输入和输出在评审中可区分。

## 5. 函数与控制流

- 优先早返回处理无效输入和权限失败，减少深层嵌套。
- 一个函数围绕一个抽象层级：Route 不混写 SQL、权限、模型调用和响应拼装的所有细节。
- 参数较多或具有可选组合时使用语义对象；不要新增含义不清的布尔参数。
- 数组转换保持可读，复杂 reduce 可改为明确循环；不为“函数式”牺牲错误处理。
- 异步函数明确 resolve、reject、取消和超时行为，不让 floating promise 成为未处理拒绝。
- `catch` 不得空吞重要失败。可以安全忽略时，用简短注释说明为何不影响结果。
- 不用魔法字符串/数字隐藏业务规则；提取到正确领域模块，而不是集中制造无结构 constants 大文件。

## 6. 数据与不可变性

- 更新 React state、Query 缓存和共享配置时保持不可变，避免调用方持有旧引用导致隐蔽联动。
- 公共函数返回共享对象时明确是否允许修改；必要时返回副本或只读视图。
- 日期、时区、精度、单位和排序写入字段/参数语义，不在调用方各自猜测。
- 数据库行、API DTO、Core 输出和 UI view model 不默认同构；跨层映射只暴露必要字段。
- 对象合并不能无意覆盖权限、身份、默认值或内部字段；尤其禁止把未校验 body spread 到写入对象。

## 7. 注释与文档

注释解释代码无法表达的**原因、约束、风险或不变量**，保持简短。命名和结构能说明的内容不重复。

推荐：

```ts
// Only the topmost picker handles Escape while nested inside a dialog.
```

不推荐：

```ts
// Declare a variable called openPanels and assign an empty array to it.
// This section explains the history and source of the implementation...
```

- 不为显然的 import、变量、getter 和逐行 JSX 写教程式注释。
- 复杂算法引用规则时注明对应领域规则或原典位置，但保持一行入口，详细内容放规范文档。
- TODO 必须有具体后续条件，不能成为永久遗留标记；已完成 TODO 删除。
- 注释随代码同步更新，过期注释比没有注释更危险。
- 公共 API/架构决策写文档，不把长篇说明塞在组件头部。

## 8. 格式与 lint

- 当前以 TypeScript、ESLint/Next 规则和文件周边风格为准，不在功能变更中顺手重排整个文件。
- 缩进、引号、分号和换行在同一个文件/模块保持一致；自动生成代码遵循生成器输出。
- 不用 eslint-disable 隐藏新引入的问题。确有框架/生成代码例外时，范围尽量小并说明原因。
- 现有 React Compiler 等警告应在触碰时逐步解决，不通过全局关闭规则制造“干净”结果。
- 如果未来引入 Prettier/Biome，先单独确定配置和迁移方式；不得同时替换 linter、格式化器并重写业务代码。

格式统一不能成为巨大 diff 的唯一内容，也不能阻碍对真实 bug 的修复。

## 9. 依赖管理

新增依赖前回答：

1. 仓库、Web 平台或现有依赖是否已经提供同等能力？
2. 它解决的是行为、性能还是仅少量样式？引入后是否真的减少维护成本？
3. 是否支持当前 Node/React/Next/Tailwind，是否影响 SSR、worker、浏览器包体和部署？
4. 维护状态、许可证、供应链和安全记录是否可接受？
5. 能否只引入所需子模块，是否带来重复底层（例如第二套图标、日期、弹层或状态库）？

使用 pnpm 并提交 lockfile 变化，版本与安装方式以官方当前文档为准。不得从社区文章复制过期包名/API。依赖升级与业务重写尽量分开；大型升级先读破坏性变更。

## 10. 重构与重写

允许为更好的设计重构或重写，但必须满足：

- 先定义现有公共行为和必须保留的安全/数据契约；高风险路径先补回归。
- 把“行为保持的重构”和“有意行为变化”分开说明与验证。
- 调用方同步迁移，旧实现完全替代后删除；不长期保留兼容 shim、feature flag 和双写路径。
- 重写遇到旧行为矛盾时，依据当前公共契约和用户裁决处理，不盲目复制 bug，也不静默改规则。
- 数据库、Agent 任务和持久化消息有特殊升级边界，按各自手册处理；代码层“删旧”不等于可以删除历史数据展示。
- 发现无关问题时记录并分开处理，除非它阻塞当前工作，不把重写无限扩张到全仓库。

## 11. 提交与变更说明

使用 Conventional Commits：`feat:`、`fix:`、`refactor:`、`chore:`、`docs:`、`test:`、`perf:` 等，scope 表达真实区域，例如 `feat(settings): ...`。

一个提交/变更组应围绕一个目的。PR/交付说明包含：

- 改了什么、为什么；
- 实际运行的命令、手动路径与结果；
- 数据库、环境变量、权限、公共契约和部署影响；
- 风险与回滚点；
- 未执行或失败验证及原因。

不提交真实密钥、临时调试代码、无关生成物、个人环境路径或用户私有数据。提交、推送和发布按用户/项目授权执行，不因完成代码自动进行。

### 11.1 分支

- 按工作域使用固定分支：MCP 用 `mcp`，Agent 用 `taibu-agent`，Core（`packages/core`）用 `core`。
- 其余改动直接进 `master`，需要隔离时用临时分支（`feat/*`、`fix/*`），合入后删除。
- 固定分支的改动合入 `master` 后一样删除，下次从 `master` 重建；不保留内容已经进 `master` 的长期分支。

## 12. 评审清单

- [ ] 类型表达真实约束，无新的逃逸断言、隐式 any 或运行时未校验输入。
- [ ] 命名与模块职责清晰，无重复公共实现、循环依赖和跨层 import。
- [ ] 控制流、错误、异步、取消和清理路径完整。
- [ ] 注释简短且解释必要原因，文档与代码同步。
- [ ] 新依赖确有必要，无重复底层或意外包体/部署影响。
- [ ] 重构不隐藏行为变化，旧实现与死代码在迁移后删除。
- [ ] 变更范围可审查，验证结果真实完整。
